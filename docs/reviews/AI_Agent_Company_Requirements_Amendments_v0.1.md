## 1. How to use this register

These are proposed refinements and additions, not approved changes to the 545-requirement baseline or the Paperclip execution pack. Existing IDs remain intact. Every row below is initially **PROPOSED / NOT TESTED**. “Shall” describes the proposed future obligation; it does not claim an implemented capability.

For each row, reviewers should record: accept / revise / reject / covered by existing requirement; rationale; affected baseline IDs; accountable owner; independent reviewer; applicable release profile; test/evidence links; decision identity/date; and approved source hashes. When an existing requirement already covers the intent, enrich its acceptance record rather than create a duplicate obligation. Rejected proposals retain their IDs and reasons.

Case IDs `AC-001` through `AC-035` below identify acceptance designs, not executed tests. They must eventually resolve to executable suites or authorized review procedures. An unapproved threshold, absent fixture, missing owner or unavailable dependency is **unresolved**, not pass or inapplicable. Numeric operational thresholds must be agreed in the relevant acceptance profile before qualification.

## 7. Acceptance-record examples to finalize

### 7.1 Example: replay-safe payment posting (AC-022)

Input contract: approved payment operation, message/usage profile, tenant identity, authorization policy, idempotency-key semantics, ledger model, expected currency precision and independently defined state machine. Fixtures include an accepted payment, duplicate/replay, key reused with changed payload, unauthorized request, timeout with unknown outcome, crash before/after durable commit and recovery/failover.

Expected results must come from the approved financial specification and oracle, not the code author's explanation. For the approved debit/credit operation, the defined ledger invariants must hold and a replay cannot create another posting. Response/status behavior, retention window and recovery timing require explicit profile values. Invalid/ambiguous authorization must not become a payment. Evidence records candidate/dependency hashes, fixture versions, environment, execution trace, ledger comparison and independent reviewer decision.

This is not an assertion of globally “exactly once” distributed delivery. Delivery may repeat; business effects must obey the defined idempotency and recovery contract. No performance result can excuse an integrity failure.

### 7.2 Example: role composition and permission (AC-009 / AC-015)

Input contract: a tenant-scoped Java task, approved technology profile, eligible skill catalogue, context/resource budget and separate author/reviewer identities. Cases include an ordinary change, ambiguous language, a misleading skill description, a request to approve one's own patch and an injected request inside source code to read another tenant's evidence.

Expected results: required skills selected according to the approved routing criteria; unrelated or conflicting capabilities excluded; authoring allowed only in the allocated workspace; production and reviewer evidence writes denied. Independent review receives frozen candidate plus requirements/approved sources without treating the author's narrative as authority. Record both quality metrics and rejected actions. Acceptable activation error and context-use bounds remain profile decisions; denial of prohibited actions is mandatory.

### 7.3 Example: vulnerability impact as a service (AC-029 / AC-030)

Input contract: customer authorization and scan window, tenant-scoped inventory/SBOM, deployed versions/configuration, approved advisory feeds and freshness bounds. Fixtures include a known affected dependency, a similarly named but different component, an uncertain transitive match, a vendor backport claim, stale inventory and an unavailable feed.

Expected results: affected / possibly affected / not affected / unknown with evidence and confidence as defined by the profile. “Not affected” requires a justified applicability decision, not only a missing scanner result. Produce a prioritized action proposal and retest plan; no unsanctioned patch, exploit or external scan. Customer evidence stays isolated; any shared learning requires separate permission and sanitization.
